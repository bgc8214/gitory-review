0. 먼저 — 초기 분석의 정정 사항

코드를 더 깊이 읽고 전제 2개를 정정합니다. 초기 분석의 "지어낸 숫자가 그대로 통과한다"는 사실이 아니었습니다. 출력 검증은 이미 동작하고 있습니다.

이전 주장실제 (코드 확인)
"지어낸 숫자가 그대로 통과한다"틀림. star_generator.py:314 가 unsupported_metrics() 를 호출해 출처 없는 수치를 잡고 NEEDS_REVIEW 로 강등. interview_llm.py:206 에서도 씀 — 잠자는 부품이 아니라 현역
"read_context 로 PR·이슈를 읽는다"틀림. StarAnalysisRequest 에는 PR/이슈 전체 컨텍스트가 없음. evidence(diff 요약) · pull_request_body(대표 PR 본문 1개) · confirmed_answers · dependency_files 뿐
"45초 예산으로"부정확. 이미 deadline_seconds=150(Spring 대기 180초, application.yml:119) · max_attempts=2 · min_call_seconds=10. 예산은 이미 넉넉함 — 새로 정할 게 아니라 쓰면 됨. 단 한 요청에 카드 8장까지(CardCreationController:35) 가능하므로 Job 전체 대기·워커 점유를 같이 재야 함
"tool_calls_made 는 전부 0 고정"틀림. /diff-evidence 는 GitHub API 호출 수를, /interview-turns 는 LLM 사용 여부를 0/1로 반환(interviews.py:69). 진짜 문제는 API마다 뜻이 다르고 STAR만 0이라는 것 — 넣기 전에 필드 의미부터 합의해야 함
"문장이 diff에 근거하는지 검증하는 완성품"과한 표현. match_commit_sha 는 SHA 대조, unsupported_metrics 는 숫자 표현의 출처 대조뿐. 문장의 의미가 diff에 근거하는지는 아무도 검증하지 않습니다 — 그건 Critic LLM(H팀 방식)이 필요한 별개 과제

정정 출처: 다른 에이전트의 교차검증(2026-10-25) + 제 재확인. 이렇게 틀린 걸 남겨두는 이유는 이 문서로 의사결정을 하실 것이기 때문입니다.

그래서 진단이 더 정확해지고, 좋은 쪽으로 바뀝니다:

검증기는 이미 전국 최상위입니다. 문제는 검증 결과가 모델에게 돌아가지 않는다는 것 — 틀리면 지우거나 딱지를 붙일 뿐, 다시 쓰게 하지 않습니다.

한 바퀴만 연결하면 됩니다. 그게 "에이전트"와 "파이프라인"의 차이입니다.

1. 지금 우리 AI가 하는 일 — 전부

LLM을 부르는 곳 4군데

어디서뭘 시키나방식실패하면
grouping_llm.py커밋 200개를 "경험 후보" 79개로 묶기한 번 호출스위치 꺼짐과 동일 — 수집만 하고 정상 종료
diff_analyzer.py커밋별 diff를 "이 커밋이 한 일" 요약으로한 번 호출커밋 메시지로 대체(COMMIT_MESSAGE 출처 표기)
star_generator.py근거 묶음 → 자소서 STAR 4칸한 번 호출
(형식 안 맞으면 재시도 1회)		타임아웃 시 4칸 비움, 형식 실패 2회면 에러
interview_llm.py ⭐빈 칸 보고 다음에 뭘 물을지 결정+질문 생성한 번 호출규칙 템플릿 질문으로 폴백

⭐ = 현재 유일하게 "모델이 무언가를 결정하는" 지점입니다. 지킬 것.

검증은 이미 이만큼 합니다 star_generator._to_response

모델이 STAR 4칸을 써서 돌려주면, 칸마다:

1. 빈 칸·빈 텍스트          → EMPTY 로 비움
2. 모델이 적은 커밋 SHA     → match_commit_sha() 로 입력 커밋과 대조
                              맞출 수 없는 SHA 는 버림
3. 근거 0개가 된 문장       → 통째로 삭제 (removed_claims 에 기록)
                              "근거 0개 문장은 화면에 뜨면 안 된다(규칙 4)"
4. 답변에만 의존한 문장     → HIGH 금지, NEEDS_REVIEW 강등
5. 출처 없는 수치           → unsupported_metrics() 로 탐지
                              "30% 개선" 같은 게 근거에 없으면 NEEDS_REVIEW 강등
6. 비밀값                   → redact_secrets() 로 가림

강점 구간입니다. 조사한 팀 중 이 정도로 출력 검증을 촘촘히 하는 팀은 손에 꼽습니다. 발표에서 "환각을 어떻게 막나요"에 이 6단계를 그대로 답하면 됩니다.

2. 그래서 진짜 빈 칸은 어디인가

⚠️ 지금 — 검증 결과가 사라짐

모델이 틀린 SHA를 적음 → 코드가 조용히 버림 → 문장이 사라지거나 "확인 필요"가 붙음 → 모델은 자기가 틀렸다는 걸 영영 모름

사용자가 보는 것: 빈 칸 또는 노란 딱지

✅ 제안 — 결과를 돌려줌

모델이 틀린 SHA를 적음 → 코드가 잡음 → "이 SHA는 입력에 없어요. 다시 쓰세요"를 모델에게 전달 → 모델이 고쳐 씀 → 통과

사용자가 보는 것: 채워진 칸 + 고친 과정

못 하는 일 4가지 (= 심사 ③에서 깎이는 이유)

지금심사 기준 문장
스스로 고치기검증 실패 = 포기(버리거나 강등)"사람이 끼어들지 않아도 끝까지 풀어내는가"
더 읽기입력으로 준 것만. 모델이 "이 커밋 더 보고 싶다"를 못 함"여러 도구와 단계를 스스로 엮어"
모르면 묻기근거 없으면 그냥 비움. 사용자에게 묻지 않음
(되묻기는 카드 생성이 끝난 뒤 별도 단계)		"도구 연동"
과정 남기기tool_calls_made 의 뜻이 API마다 다름 — diff-evidence는 GitHub 호출 수, interview는 0/1, STAR·groups는 0 고정. 통일된 계측이 없음심사자가 볼 증거가 없음

검증의 한계도 분명히. 지금 검증은 SHA가 입력에 있나와 숫자의 출처가 있나 두 가지입니다. "이 문장이 diff 내용과 맞는가"는 검증하지 않습니다 — 모델이 근거 SHA를 정확히 달고 숫자를 안 쓰면서 내용을 지어내면 못 잡습니다. 이건 Critic LLM이 필요한 별개 과제라 이번 범위에서 뺐습니다.

3. 설계 — 초안 에이전트

카드 초안(DRAFT Job)의 StarGenerator.generate() 안쪽만 바꿉니다. Spring·FE·DB 계약 변경 0.

3-1. 도구 3개 (+1개 보류) — 모델이 쓸 수 있는 행동

※ 정정 반영: PR/이슈 전체 컨텍스트는 요청에 없으므로 읽기 도구는 요청 안의 재료만 다룹니다.

read_evidence(sha) 부품 있음

재료: request.evidence[] (DiffEvidence — sha · summary · changed_paths · source)

지금은 모든 근거를 한 번에 payload에 때려 넣습니다. 이걸 "목록만 먼저 주고, 필요한 것만 펼쳐 읽게" 바꿉니다. 근거가 20개여도 모델이 관련된 5개만 깊이 읽으면 되고, "무엇을 읽을지 고르는 행위" 자체가 ③의 증거가 됩니다.

새 코드: 조회 함수 + payload 분리 ~25줄

check_draft(draft) 완성품 재사용

재료: evidence_checks.match_commit_sha() · unsupported_metrics() — 이미 _to_response 에서 쓰는 그 함수들

지금 맨 끝에서 한 번 하는 검증을 루프 안으로 끌어올려 모델이 결과를 받게 합니다. 반환은 사람이 읽는 문장으로:

{"ok": false, "problems": [
  {"slot":"R", "type":"UNKNOWN_SHA", "detail":"a1b2c3d 는 이 경험의 근거 목록에 없습니다"},
  {"slot":"A", "type":"UNSOURCED_NUMBER", "detail":"'30% 개선' 의 출처를 근거에서 찾을 수 없습니다"}
]}

새 코드: 어댑터 ~30줄 (판정 로직은 기존 함수 그대로)

ask_user(slot, question) Spring 변경 필요 — 후순위

재료: 되묻기 인프라 — 단 소유자가 Spring

두 번 고쳐도 근거가 없으면 지어내지 말고 빈 칸으로 두되 질문을 남긴다는 아이디어입니다.

교차검증에서 걸러진 제 착각 — "20줄이면 재사용"이라고 썼는데 틀렸습니다. 질문의 순번·횟수 제한·영속 저장은 전부 Spring InterviewAskService 가 소유하고(interviews.py:45 에 명시), AI 서비스는 질문을 생성해 반환만 합니다. 카드 초안 경로(CardDraftRunner)는 되묻기 저장 경로와 아예 다릅니다. 루프 안에서 질문을 만들어 저장·중단·재개하려면 Spring Job/질문 생명주기를 바꿔야 합니다.

그래서 이번 범위에서 뺍니다. 대신 같은 효과를 싸게 내는 대안 — 에이전트가 "이 칸은 근거가 없어 못 씁니다"를 응답 필드로 올리고(insufficient_reason 은 이미 있음), 화면이 그 칸에 기존 "답변하기" 버튼을 노출. 계약 변경 없이 "모르면 묻는다"가 사용자에게 같은 모습으로 보입니다.

submit(draft) 부품 있음

재료: StarDraftOutput 스키마 그대로

검증 통과한 초안을 확정. 지금의 _to_response 가 그대로 받아서 후처리합니다 — 마지막 안전망은 유지(루프가 놓쳐도 기존 6단계 검증이 또 걸러냄).

3-2. 루프와 예산 — 이미 있는 상한을 쓴다

예산 (기존 StarGenerationLimits 그대로 활용)
  deadline_seconds   150   # Spring 대기 180초보다 짧게 — 이미 설정돼 있음
  min_call_seconds    10   # 남은 시간이 10초 미만이면 새 호출 안 함 — 이미 있음
  max_repair_rounds    2   # ← 새로 추가 (고쳐쓰기 최대 2번)
  max_tool_calls       8   # ← 새로 추가 (읽기 포함 전체 상한)

흐름
  1. 근거 목록(요약만) + 과제를 모델에게 제시
  2. 모델이 read_evidence 로 필요한 근거를 펼쳐 읽음        ← 스스로 고름
  3. 초안 작성
  4. check_draft
       ├─ ok ──────────────→ submit → 끝                    # 대부분 여기
       └─ 문제 발견
             ├─ 남은 라운드 있음 → 문제 목록을 모델에게 주고 재작성  ← 스스로 고침
             └─ 라운드 소진 → 그 칸만 비우고 insufficient_reason 기록   ← 모르면 비움
                              # 화면이 그 칸에 "답변하기" 노출 → 계약 변경 0
  5. 시간 초과·예외 → 현행 단발 경로로 폴백                  # 지금과 100% 동일

왜 안전한가 — ⓐ 폴백이 "지금 코드"라 루프가 통째로 죽어도 서비스는 오늘과 같습니다 ⓑ 기능 스위치(CARD_AI_DRAFT_AGENT_ENABLED)로 감싸 꺼진 채 머지 → 운영에서 켜고 확인 → 이상하면 끄기 — #190·#193에서 이미 쓴 방식 ⓒ 출력은 여전히 _to_response 6단계 검증을 통과해야 하므로 품질 하한이 내려갈 수 없습니다

3-3. 프롬프트에 추가할 것

시스템 프롬프트에 행동 규칙이 들어가야 합니다. 상위팀(G팀)이 프롬프트에 판단 원칙을 명문화해 점수를 받은 지점입니다.

- 근거에 없는 수치·고유명사를 쓰지 않는다. 확신이 없으면 그 칸을 비우고 ask_user 로 묻는다.
- 문장마다 근거 SHA 를 단다. 입력 목록에 없는 SHA 를 지어내지 않는다.
- check_draft 가 문제를 돌려주면 그 문제만 고친다. 통과한 칸은 건드리지 않는다.
- 근거를 다 읽을 필요는 없다. 쓰려는 문장에 필요한 것만 읽는다.

3-4. 화면·기록에 보일 것 현장 ③ 20점의 핵심

루프를 만들어도 사용자가 못 보면 심사에서 0점입니다. 과정을 남기고 보여줘야 합니다.

4. 되묻기 강화 — 답을 평가하고 더 묻기

1일 · 부품 상태 확인 필요

지금: 질문 → 답변 → 칸 저장 → 끝. 답이 부실해도 한 번이면 통과합니다.

레포에 llm_answer_sufficiency_evaluator.py("B-2 답변 충분성 판정기")가 있습니다. 이걸 되묻기 뒤에 붙여:

답변 ──→ 충분성 판정 ──충분──→ 칸 저장 (지금과 동일)
             │
             └─불충분 ──→ "언제·얼마나가 비어 있어요" 후속 질문 1회 ──→ 저장
                           # 상한 1회. 심문이 되면 사용자가 떠난다

확인 필요 — 이 평가기가 지금 어디서 호출되는지 먼저 grep 하세요. 이미 운영에서 쓰고 있다면 이 제안은 "연결"이 아니라 "강화"로 범위가 바뀝니다. (제가 unsupported_metrics를 "잠자는 부품"이라 잘못 본 전례가 있어 못 박습니다.)

5. 그룹화 라우팅 — 판단을 아끼는 것도 판단

1일 · 선택 과제 · D팀(상위권) 패턴

지금은 커밋 200개를 통째로 LLM에 넘깁니다. 그런데 그중 상당수는 규칙으로 충분합니다 — 같은 PR에 속한 커밋들은 LLM 없이도 한 묶음이 맞으니까요.

커밋 목록
  ├─ 같은 PR 소속 (명확)  ──→ 규칙으로 묶음. LLM 호출 안 함
  └─ 떠도는 커밋 (애매)   ──→ LLM 에게 판단 요청
                              # 호출량·비용 감소 + "왜 agentic 인가"의 설명

발표 수치로도 좋습니다 — "LLM 호출의 N%를 규칙이 대신합니다". D팀는 이 설계를 그래프 구조로 표현해서 ⑤ 만점을 받았습니다.

6. 구현 순서 — 4단계로 쪼개기

이 팀 장기인 "작게 쌓아 올리는 PR"에 맞춰 나눴습니다. 각 단계가 독립적으로 머지 가능합니다.

#PR내용검증걸리는 시간
1계측 의미 통일 + 채우기4개 API의 tool_calls_made 뜻을 하나로 정의 → STAR·groups도 채움 + 호출 수·토큰 로그. 기능 변화 0네 API가 같은 뜻으로 숫자를 내나반나절
2검증기 분리_to_response 안의 검증을 check_draft() 로 추출. 동작 동일(순수 리팩터링)기존 테스트 전부 통과반나절
3고쳐쓰기 루프 ★검증 실패 → 문제 목록 전달 → 재작성 ≤2회. 스위치로 감쌈스위치 끄면 지금과 동일, 켜면 trace 생성1.5일
4읽기 도구 + trace UIread_evidence 로 근거를 골라 읽게 + 화면에 과정 표시후보 20개로 before/after 비교1.5일

3번까지만 해도 ③은 확보됩니다. 4번은 "영상이 더 멋져지는" 단계라, 시간이 없으면 3번에서 멈추고 발표 준비로 넘어가세요. 1·2번은 리스크가 0이라 오늘이라도 시작 가능합니다.

7. 측정 — 만들었으면 숫자로

루프를 넣었으면 효과를 재야 ⑥(AI 품질 점검)이 같이 올라갑니다. 심사 문장이 "실패를 분석해 고친 기록"이라 문자 그대로 들어맞습니다.

측정방법
검증 통과율같은 후보 20개를 스위치 끄고 / 켜고 각각 생성 → 첫 검증에서 문제가 난 칸 비율 비교
빈 칸 비율NO_EVIDENCE 로 비워진 칸 수 — 루프가 있으면 줄어야 함
NEEDS_REVIEW 비율노란 딱지 붙은 칸 — 줄어야 함
비용Job 당 LLM 호출 수·토큰 — 늘어난 만큼이 품질의 대가. 솔직히 적는 게 신뢰를 삼

결과는 ai/evals/MEASUREMENTS.md 에 D팀 규율로 — 모델명 필수 · 0건도 분모와 함께(0/80) · 날짜 · 데이터셋 출처.

발표 한 줄로: "고쳐쓰기 루프를 넣고 빈 칸이 N% → M% 로 줄었습니다. LLM 호출은 카드당 평균 1.2회 → 1.6회 늘었습니다."

8. 리스크와 반론

우려답
"마감 17일 전에 AI 핵심을 건드린다?"단계 1·2는 동작 변화 0. 3은 스위치로 감싸고 폴백이 현행 코드. 최악의 경우에도 오늘의 서비스
"비용·시간이 늘어난다"늘어나는 건 검증에 실패했을 때뿐이고, 그때 늘어나는 게 가치입니다. 예산(150초·10초 하한)은 이미 코드에 있음. 제안 5(라우팅)가 반대쪽에서 호출을 줄임
"LangChain 같은 걸 써야 하지 않나"아니요. B팀(상위권)가 프레임워크 없이 도구 루프를 짜서 증명했습니다. 도구 3개짜리 루프는 직접 짜는 게 더 작고, "직접 이해하고 만들었다"가 발표·면접에서 더 셉니다
"되묻기 자율성만으로 ③ 안 되나"상위권 팀들 중 4팀이 도구 루프를 가졌습니다. "모델이 질문을 고른다"는 설명이고 trace는 증거입니다 — 심사는 증거를 봅니다
"BE 수정이 필요하면?"교차검증에서 ask_user 가 Spring 생명주기 변경이 필요하다고 확인돼 범위에서 뺐습니다. 남은 제안은 전부 AI 서비스 안에서 끝나고 응답 계약도 그대로입니다(trace 필드만 추가)
