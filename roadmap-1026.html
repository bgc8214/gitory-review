팀 회의 결정사항 — 심사 기준 대조

2026-10-25 회의에서 나온 7가지를 심사 배점·제출물 요구사항과 대조하고, 이미 있는 재료와 남은 일을 정리했습니다

결론부터 — 7가지 중 6가지가 심사에서 점수가 되는 방향입니다. 특히 ③ 에이전트 일괄 처리와 ⑦ 진행 표시는 가장 큰 결손(Agentic 30점)을 정확히 겨냥하고 있습니다.

근거: origin/develop 코드 확인 · 심사 100점 문서 · 업계 사례

목차 한눈에 — 7가지 판정 ① 공고 매칭 개편 ② 카드 → 공고 추천 ③ 에이전트 일괄 처리 ④ AI 자소서 + 가격 근거 ⑤ 진행 상태 노출 ⑥ 에러 메시지 점검 ⑦ 프론트 UI/UX 점검 실행 순서 — 남은 16일

전체적으로 좋은 방향입니다. 특히 ③·⑤·⑥은 심사 기준 문장에 직접 대응합니다. 다만 남은 기간이 제출까지 16일이라 전부 할 수는 없고, 아래 §8에 순서를 제안했습니다.

①공고 매칭 개편 — 자격요건 선필터 + 상위 몇 개만 LLM 판정방향 적절
이미 있는 재료

· schemas/matching.py 에 ExperienceLevel(ENTRY/EXPERIENCED/UNSPECIFIED) + min_years 가 이미 추출·저장되고 있습니다 — 선필터 재료가 이미 있습니다.

· ai/evals/JOB_MATCHING_EVALUATION.md + 케이스 JSON 2종 + 평가 스크립트 — 개편 전후를 비교할 평가셋이 이미 있습니다.

지금 문제 (코드 확인)

talent_matcher.py:28 의 maximum_distance = 0.4 — 코사인 거리 하나로만 판정합니다. 그래서 "Java 3년 이상"에서 "Java"만 보고 "3년"은 못 봅니다. 팀 진단이 코드와 정확히 일치합니다.

심사 관점에서 플러스인 이유 — "안 맞는 건 규칙으로 먼저 거르고, 애매한 것만 LLM" 은 심사 ⑤의 "단계 분기" 그 자체이고, 캠퍼스 전체 중 D팀(상위권)가 "명확한 건 LLM을 안 부른다" 로 점수를 받은 설계와 같습니다.

F팀(동급) 패턴과도 일치 — "숫자는 코드가 계산하고 LLM은 근거 연결만". 연차·경력 같은 딱 떨어지는 조건은 규칙이, "이 경험이 이 조건을 받치나" 같은 판단만 LLM이.

제안 하나 — 등급을 서버 안에서만 쓰는 건 맞는데, 완전히 숨기면 "왜 이 공고가 안 보이지"를 설명할 길이 없어집니다. "더 보기"를 누르면 제외 이유를 볼 수 있는 길은 남겨두는 게 좋습니다. 발표에서 "왜 이것만 보여주나요?" 질문의 답이기도 합니다.

📏 개편 전후를 평가셋으로 측정해두면 심사 ⑥("실패를 분석해 고친 기록")에 그대로 들어갑니다. 평가 스크립트가 이미 있으니 숫자만 뽑으면 됩니다.

②카드를 만들면 공고가 추천되게서사 완성

제품 서사가 여기서 닫힙니다. 지금은 "커밋 → 카드"에서 끝나고 매칭은 따로 들어가야 하는데, 카드를 만든 직후에 "이 경험으로 지원할 만한 공고"가 나오면 "왜 이걸 쓰는가"가 한 흐름으로 설명됩니다.

심사 효과

· ① 명확성(10) — "문제 → 기능 구성이 일관되게 연결"의 마지막 고리
· 현장 ⑤ 차별성(15) — "자소서 첨삭 AI"들과 결정적으로 갈리는 지점. 근거 커밋이 붙은 경험이 실제 공고 조건과 연결되는 건 우리만 가능
· 시연 영상의 엔딩 — 10/25 실측 시나리오도 매칭으로 끝났는데, 그게 자연스럽게 이어집니다

💡 구현은 ①이 끝난 뒤가 맞습니다. 매칭 품질이 낮은 상태로 추천을 붙이면 오히려 역효과예요.

③카드 만드는 과정을 에이전트가 한 번에 — 사람 개입 축소최우선

우리가 가장 많이 잃고 있는 항목을 정확히 겨냥합니다. 심사 ③ 기준 문장이 "사람이 끼어들지 않아도 핵심 시나리오를 끝까지" 인데, 지금은 단계마다 버튼을 누릅니다.

배점

멘토 ③ 10점 (현재 4) + 멘토 ⑤ 15점 의 "도구 연동" 칸 + 현장 ③ 20점 = 실질 30점

설계 방향 — 이미 문서로 있습니다

Agentic 쉽게(비유·단계별 할 일) / 상세 설계(도구·루프·PR 분할)

핵심은 "검사 결과를 AI에게 돌려주는 것" 하나입니다. 검사기(evidence_checks.py)가 이미 있고, 지금은 검사해서 틀리면 버리거나 딱지만 붙이는데 그걸 AI에게 알려주고 고칠 기회를 주는 겁니다.

"사람 개입 축소"의 범위를 정할 때 주의 — 전부 자동화하면 안 됩니다. 본인 경험을 확인하는 단계는 사람이 있어야 제품이 성립합니다(지어낸 자소서가 되면 안 되니까요).

업계도 같습니다 — 조사한 10개 제품 중 v0·Bolt만 승인 게이트가 없고 그건 샌드박스라서입니다. 나머지는 전부 반영 전 게이트가 있어요.

→ 발표에서 "자동으로 하는 부분 / 사람이 확인하는 부분"을 한 장으로 선 긋기. 확정 버튼이 사람인 건 약점이 아니라 설계입니다.

업계 근거로 쓸 수 있는 것 — 재시도 상한(우리 제안 2회)이 Lovable 10회·Cursor ~3회·Bolt 경고와 같은 관행입니다. "왜 2번인가요?" 질문의 답이 됩니다. (업계 사례 §4)

④AI 자소서 기능 + 가격 산정 근거 (약 100원)발표 무기
이미 있는 흔적

UsageEventNames.java 에 cover_letter_created · cover_letter_copied · cover_letter_edited 가 이미 정의돼 있습니다 — 계획이 코드에 반영돼 있다는 뜻입니다.

⚠️ 다만 프론트 전송부가 아직 없습니다(track.ts 에 해당 이벤트 없음). 기능을 넣을 때 전송도 같이 붙여야 숫자가 쌓입니다.

ai/evals/REPOSITORY_COST_MEASUREMENT.md — 레포당 운영 비용을 이미 측정해뒀습니다. 자소서 단가도 같은 방식으로 재면 됩니다.

"100원"을 설득력 있게 만들려면

ⓐ 원가 분해 — 토큰 수 × 모델 단가 = 실제 비용. 여기에 마진을 왜 그렇게 뒀는지.
ⓑ 비교 대상 — 자소서 첨삭 서비스, AI 글쓰기 도구의 가격대. "우리는 근거 커밋이 붙는다" 가 같은 가격에서의 차별점.
ⓒ 대안 비용 — 사용자가 직접 쓰면 몇 시간? 첨삭 서비스는 얼마? 100원이 싸 보이는 기준점을 제시.

💡 Lovable은 작업 중 "Credits used"를 실시간 표시합니다. 우리도 자소서 생성 시 "이번 생성 비용"을 보여주면 가격 설계를 제품으로 증명하는 셈이 됩니다. (업계 사례 §2)

⑤AI가 작업 중임을 화면에 노출 — 기다림을 견디게최우선

팀의 진단이 정확합니다 — "사용자에게 노출이 되어야 기다리는 시간이 허용되고 좀 더 agentic한 느낌이 있다". 이건 업계 조사 결과와 정확히 일치합니다.

업계 공통 패턴 (10개 제품 조사)

Anthropic이 권장하는 에이전트 UI 패턴이 "추론은 감추고 각 단계마다 상태 한 줄" 입니다. Lovable은 "Working for"(경과 시간) + "Credits used"(현재 비용) 를 계속 갱신하고, Devin은 단계별 소요시간을 보여줍니다.

→ 길게 설명할 필요 없고 "지금 무엇을 하는 중" 한 줄이면 됩니다.

우리에게 이미 있는 것

· frontend/src/features/cards/DraftProgress.tsx — 카드 초안 진행률 표시 컴포넌트가 이미 있습니다 ("카드 초안 1/2장", 퍼센트, Track 바)
· 분석 화면의 4단계 진행 표시 (10/25 실측에서 확인)
· JobLiveness 컴포넌트

→ 새로 만드는 게 아니라 되묻기·자소서에도 같은 패턴을 쓰는 일입니다.

③과 짝입니다

③의 에이전트 루프를 만들어도 화면에 안 보이면 심사에서 0점입니다 — 전부 서버 안에서 벌어지니까요. ⑤가 ③을 점수로 바꿔주는 장치입니다.

표시 내용은 성공만이 아니라 실패→수정까지. "근거 3건 읽음 → 검증 실패 → 다시 씀 → 통과" 가 있어야 "스스로 고친다"가 증명됩니다. 성공만 보이면 그냥 진행 표시줄입니다.

기본은 접어두기(업계 공통 패턴 ①). 펼치면 상세가 나오는 구조. v0의 원칙처럼 기본 화면은 결과만.

⑥에러 메시지 점검 — 사용자가 뭘 해야 하는지기준 문장에 직접 대응

심사 ⑦의 기준 문장에 그대로 들어 있습니다 — "출력 가드레일·예외 처리·장애 대응·실패 시 사용자 안내를 갖춰…" (10점)

생각보다 이미 잘 돼 있습니다 — 코드 확인

frontend/src/lib/labels.ts 가 에러 코드별로 "제목 + 다음 행동" 2단으로 돼 있습니다:

AI_UNAVAILABLE      분석 도우미가 잠시 응답하지 않아요
                    → 잠시 뒤 다시 시도해 주세요.

GITHUB_RATE_LIMITED GitHub 요청 한도에 걸렸어요
                    → 한도가 풀리면 읽던 데서 이어서 읽어요.

DRAFT_TIMEOUT       시간 안에 다 채우지 못했어요
                    → 채운 칸까지 보여 드려요. 나머지는 칸 하나씩 다시 해 볼 수 있어요.

에러 코드 7종이 정의돼 있고(JobErrorCode), useJobRetry 로 재시도 가능 여부까지 판단합니다.

그래서 점검의 방향

"없는 걸 만드는" 게 아니라 "빠진 곳을 찾는" 작업입니다:

· 7종이 전부 화면에 쓰이나 — 정의만 되고 안 쓰이는 코드가 있는지
· 다음 행동이 실제로 가능한가 — "다시 시도해 주세요"라고 썼는데 버튼이 없으면 안내가 아님
· AI 실패 경로 — 자소서·되묻기 실패 시 안내가 있는지
· 새로 추가될 기능(자소서·매칭 개편)에도 같은 2단 구조 적용

💡 발표 자료에 에러 안내 2단 구조를 한 장으로 넣으면 ⑦의 증거가 됩니다. 이건 이미 가진 강점인데 안 보이는 쪽입니다.

⑦프론트 UI/UX 점검범위 제한 권장
주의 — 이미 강한 영역입니다

심사 ② 완성도는 현재 9/10 입니다. 10/25 실측에서 전 구간 중단 0건이었고, 편의 요소도 많습니다 — 읽기 범위 사전 동의, 새로고침 복구, 취소 버튼, 자동 저장, "빈 채로 확정됩니다" 경고, 확정 전 요약 모달.

frontend/docs/ 에 UI 점검 기록이 127개 쌓여 있습니다.

가장 큰 리스크는 "발표 직전에 넣은 변경이 깨지는 것" 입니다. ②에서 9점을 지키는 게 새 점수를 따는 것보다 중요합니다.
