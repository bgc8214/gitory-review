2. 제품별 — 과정을 어떻게 보여주나

우리에게 참고가 되는 것 위주로. 공식 문서에서 확인한 리터럴은 이렇게 표기했습니다.

Devin실패 표시가 가장 명시적 — 우리가 가장 많이 배울 제품

Issue Timeline으로 문제를 색으로 분류합니다 — 🔴 큰 영향 / 🟡 중간 / ⚪ 주요 사건 / 🟢 가치 제공. 문서가 직접 드는 예: 빌드 실패, 환경 설정 문제, 코드베이스에 대한 잘못된 가정, 범위 모호함.

문서 표현이 핵심을 찌릅니다 — "Devin이 어디서 진전을 냈고, 어디서 막혔고, 어떻게 회복했는지"

work log는 단계마다 접었다 펼 수 있고, 펼치면 회고 + 타임스탬프 + 단계별 소요시간이 나옵니다. 세션 비용도 ACU 단위로 노출합니다.

💡 "어디서 막혔고 어떻게 회복했는지" — 이게 심사 기준 ③의 "스스로 풀어내는가"에 대한 가장 좋은 답변 형식입니다.

LovableUI 문자열과 과금 구조가 가장 잘 문서화됨

activity card가 파일 편집·명령·웹 검색·브라우저 테스트를 추적하고, 작업 중에는 Working for(경과 시간)와 Credits used(현재 비용)가 계속 갱신됩니다.

요약 카드가 기본이고 클릭하면 전체 단계 타임라인 + 파일 변경 상세가 펼쳐집니다.

Try to fix 버튼은 로그를 스캔해 원인을 찾은 뒤 수정합니다. 무료 10회, 24시간 후 재충전. 최신 빌드가 실패 중이면 배포 자체를 차단합니다.

💡 "경과 시간 + 현재 비용을 실시간으로" — 우리도 카드 생성 중에 간단히 넣을 수 있습니다.

💡 실패도 정해진 문구로 보여준다는 게 포인트입니다. 우리도 "근거를 찾지 못해 이 칸은 비웠습니다" 같은 고정 문구를 정해두면 좋습니다.

lint 자동 수정 루프가 있고 파일당 약 3회 상한입니다2차. 그럼에도 포럼에 "무한 lint 루프" 버그 리포트가 있습니다 — 상한을 걸어도 샌다는 교훈.

v0 (Vercel)정반대 전략 — 실패를 의도적으로 숨김

전제가 솔직합니다 — "LLM이 생성한 코드는 10% 정도 빈도로 오류를 가질 수 있다"

그래서 스트리밍 도중 출력을 조작하고, 결정론적 수정기 + AST 분석 + 전용 소형 모델로 뒤처리합니다. 원칙이 명시돼 있어요 — "스트리밍 중에 일어나기 때문에 사용자는 중간의 잘못된 상태를 절대 보지 않는다"

5. 개발자들은 뭘 계측하나

표준은 아직 미완성입니다 1차 · GitHub API로 확인

OpenTelemetry GenAI 규약 — 2026-10 기준 릴리스 0건, 태그 0건, 전 속성이 Development 단계. 레포도 2026-05에 분리 신설됐고 README의 Schema URL이 아직 TODO입니다.

→ 표준을 따라야 한다는 부담을 가질 필요 없습니다. 다만 속성 이름만 빌려 쓰면 나중에 도구를 붙일 때 마이그레이션이 싸집니다.

모든 도구가 공통으로 남기는 7가지

#값왜 필요한가
1trace id + 부모·자식 관계한 요청 안의 수십 호출을 하나의 트리로 묶는 뼈대. 이게 없으면 나머지 6개가 전부 떠다니는 로그가 됨
2입력 / 출력재현의 전제. 단 PII 때문에 표준에서는 기본 미수집
3시작·종료 시각, 지연
(+ 첫 토큰까지)		어느 단계가 느린지. 스트리밍에서는 총 지연보다 첫 토큰까지가 체감 지표
4토큰 (입력/출력/캐시/추론 분리)합계만으로는 최적화 지점이 안 보임
5비용 (USD)토큰은 모델마다 단가가 달라 비교 불가
6상태 / 에러 / 예외에이전트는 부분 실패가 정상 상태(툴 1개 실패 후 재시도). 플래그 없이는 루프와 정상 동작을 구분 못 함
7단계 유형 (LLM/도구/검색/에이전트)집계의 축. "지연의 80%가 검색", "비용의 60%가 서브에이전트" 같은 문장이 여기서 나옴

왜 "trace"가 중요한가 — 단위의 불일치

사용자 눈에는 요청 1건이지만 내부에서는 LLM 호출 N회 + 도구 M회가 루프를 돕니다. 개별 호출 로그만으로는 "왜 30초 걸렸나", "왜 0.4달러 나갔나"에 원리적으로 답할 수 없습니다 — 귀속시킬 부모가 없으니까요.

에이전트에서는 한 발 더 나갑니다. LangSmith는 trajectory(에이전트가 처음부터 끝까지 밟은 경로)를 별도 개념으로 둡니다. 즉 "출력이 맞았나"만이 아니라 "어떤 경로를 밟았나"가 1급 관측 대상이고, 그건 트리 없이는 재구성이 안 됩니다.

Langfuse 문서의 한 줄이 직설적입니다 — "LLM 애플리케이션은 본질적으로 비결정적이다. 그래서 관측 도구 없이 디버깅하는 건 추측에 가깝다."

6. 우리가 할 것 — 작은 팀의 최소 5순위

상용 도구 없이 직접 구현한다면 이 순서입니다. 각각 왜 그 순위인지 근거를 달았습니다.

1순위. trace_id를 요청 진입점에서 발급해 모든 호출에 심기

컬럼 5개면 됩니다 — trace_id, parent_id, seq, step_type, started_at.

이것 하나만 해도 나머지가 전부 분석 가능해지고, 안 하면 나머지를 다 해도 분석이 안 됩니다. 조사한 6개 상용 도구가 예외 없이 이걸 1순위 뼈대로 삼습니다.

→ 발표 효과: "한 요청 = 한 trace" 트리를 보여주는 것 자체가 데모가 됩니다. step_type은 업계 분류(LLM·도구·검색·체인·에이전트)를 그대로 빌리면 설계 논쟁 없이 끝납니다.

2순위. 호출마다 상태 + 에러 유형 + 시도 횟수 기록

에이전트의 지배적 장애 모드는 크래시가 아니라 조용한 무한 재시도 루프입니다. 4절의 증거가 전부 이걸 가리킵니다.

→ attempt 컬럼 하나가 "데모 중 토큰이 다 타버린" 사고를 막아줍니다. 발표 당일 리스크 관리이기도 합니다.

3순위. 토큰(입력/출력 분리) + 지연, trace 단위로 합산

호출별 수치만으로는 "이 기능이 요청당 얼마/몇 초"를 말할 수 없는데, 발표에서 가장 임팩트 있는 숫자가 정확히 그 둘입니다.

→ 단가표를 하드코딩한 dict로 두고 곱하면 비용까지 나옵니다. Q&A "운영비 얼마 드나요"의 답.

4순위. 프롬프트 본문은 기본 끄고, 켤 수 있게만

표준이 프롬프트·응답 본문을 전부 Opt-In으로 지정하고 "사용자 개인정보를 포함할 가능성이 높다" 경고를 답니다.

→ 환경변수 하나로 토글되게 해두면 로컬 디버깅은 편하면서 PII 사고와 저장소 폭발을 동시에 막습니다. 우리는 GitHub 데이터를 다루니 더 중요합니다. 발표에서 설계 성숙도로 어필할 포인트.

5순위. 같은 이벤트 스트림으로 사용자 UI까지 그리기

2~3순위에서 쌓은 단계 이벤트를 그대로 프론트에 흘려 "지금 무엇을 하는 중"을 한 줄로 띄우고 상세는 접어둡니다.

계측과 UI를 따로 만들지 않는 게 핵심이고, 이건 Anthropic이 display: "updates"를 권장하는 바로 그 패턴입니다.

→ 각 단계에 "표시용 문장" 필드를 하나 두면 UI가 거의 공짜로 나옵니다. Claude Code가 activeForm(진행형 표현) 필드를 두는 것과 같은 방식 — 예: "근거를 읽는 중".

하지 말 것 — 처음부터 OpenTelemetry SDK 붙이기. 5절에서 본 대로 gen_ai.*는 릴리스 태그 0개에 전 속성이 Development라 스펙이 움직입니다. 속성 이름만 빌려 쓰세요 — 나중에 Langfuse(코어 MIT, 무제한 무료 셀프호스팅)로 갈아탈 때 마이그레이션이 거의 공짜가 됩니다.
